# Спецификация IR — оглавление

Чистовое описание формата. Порядок изложения: **КОМПОНЕНТ → СХЕМА → ПЛАТА** —
от кирпича к изделию.

Одна сущность — одна страница. Сущность, встречающаяся в нескольких контекстах
(например `<line>` — и в символе, и в корпусе, и на плате), описана **один раз**;
из остальных глав на неё ведёт ссылка. Такие строки помечены **↗**.

> ⚠ **[reasoning.md](reasoning.md) — что мы поменяли в самом IR по ходу вычитки.**
> Там же статус каждой правки: решено / сделано в коде. Пока не сошлись —
> спека описывает будущее, а код живёт по-старому.

> **Статус: `V0` — спецификация написана и вычитана целиком**, все четыре главы.
> По итогам внешней вычитки правится: [журнал](reasoning.md) ведёт список.
>
> Это описание **целевого** формата. Код Babel местами живёт по-старому —
> расхождения перечислены в [reasoning.md](reasoning.md) пометкой
> «в коде не сделано».

## 0. Общее — сквозные правила

Действуют во всех трёх главах. Читать до всего остального.

| Страница | О чём |
|---|---|
| [Единицы и координаты](units.md) | Целые микрометры, `int32`, Y вверх, углы — целые миллиградусы |
| [Модель слоёв](layer-model.md) | Знаковое число `[!][-]N`. Механизм один, пространства у схемы и платы **разные** |
| [`<layer>`](layer.md) | Объявление слоя — имя, цвет, видимость. Схемные у проекта, платные у платы |
| [Имя, атрибут, плейсхолдер](naming.md) | Формальная модель: три разных факта, которые нельзя смешивать |
| [Плейсхолдеры](placeholders.md) | Режим по первому символу: `>` подставить, `=` вычислить |
| [Рамка листа](frame.md) | Страница на холсте схемы — символ с `<shape>` на слое `98` |
| [Символ питания](power-symbol.md) | Ярлык с именем шины — символ с выводом `sup` |
| [Кастомный пад](custom-pad.md) | Площадка произвольной формы — медь, отверстие и SMD-носитель имени |

### Примитивы графики

Кирпичи, из которых сложена вся геометрия — в символе, в корпусе, на схеме и на плате.

| Сущность | О чём |
|---|---|
| [`<line>`](line.md) | Отрезок |
| [`<arc>`](arc.md) | Дуга — концевая форма (две точки + прогиб) |
| [`<shape>`](shape.md) | Прямоугольник или круг, в т.ч. массив |
| [`<polygon>`](polygon.md) | Заполненный многоугольник (модель пера) |
| [`<vertex>`](vertex.md) | Вершина полигона, с прогибом |
| [`<text>`](text.md) | Текстовая аннотация |

### Атрибуты

| Сущность | О чём |
|---|---|
| [`<attr>`](attr.md) | Пользовательский атрибут — имя, значение, тип |

Отдельного тега `<description>` нет: описания — обычные атрибуты
(`description`, `sym_desc`, `fp_desc`).

| ↗ [`<attr>`](attr.md) | Атрибуты компонента |
| [`<footprint>`](footprint.md) | Корпус — **пул**, имя уникально в библиотеке |
| ↗ [`<line>`](line.md) [`<arc>`](arc.md) [`<shape>`](shape.md) [`<polygon>`](polygon.md) [`<text>`](text.md) | Графика корпуса — шёлкография, сборочный, контуры |

| [`<model3d>`](model3d.md) | Привязка 3D-модели к корпусу |
| [`<device>`](device.md) | **Устройство** — соответствие символа корпусу; несёт маппинг и атрибуты |
| [`<map>`](map.md) | Вывод и его пады — списком; гейт отдельным полем |

| Сущность | О чём |
|---|---|

| [`<class>`](class.md) | Пул именованных наборов правил — ширина, сверло |
| [`<schematic>`](schematic.md) | Схема — холст изделия; она же содержимое модуля |
| [`<part>`](part.md) | Деталь — обозначение, выбранное устройство, значения атрибутов |
| ↗ [`<attr>`](attr.md) | Значения, переопределённые на детали |
| [`<compinst>`](component-instance.md) | Размещение одной секции детали на холсте |

| [`<net>`](net.md) | Цепь |
| ↗ [`<attr>`](attr.md) | Атрибуты цепи: `class`, напряжение, `max_current` |
| [`<segment>`](segment.md) | Сегмент цепи — связная группа проводов; точки и петельки на пересечениях |
| ↗ [`<line>`](line.md) | Провод внутри сегмента |
| [`<label>`](label.md) | Метка цепи |
| [`<pinref>`](pinref.md) | Подключение к выводу инстанса — детали **или** модуля |
| [`<variant>`](variant.md) | Вариант сборки — что не паяем и с какими значениями |
| [`<note>`](note.md) | Блок markdown — «textbox»; ширина задана, высота от контента |
| ↗ [`<line>`](line.md) [`<text>`](text.md) | Оформление листа |

### Импорт и экспорт

Не устройство формата, а **обязательства конвертера**: что сохраняется, что
аппроксимируется, что теряется и на что обратить внимание после переноса.

| Страница | О чём | |
|---|---|---|
| [Общий контракт](appendix/conversion.md) | Четыре обязательства, обязательность лога, гигиена источника, выгрузка библиотеки из проекта | ✅ |
| [Из/в Eagle](appendix/conversion-eagle.md) | Самый близкий из трёх. Три уровня Eagle против двух наших: `technology` разворачивается в отдельные компоненты | ✅ |
| [Из/в KiCad](appendix/conversion-kicad.md) | Расхождение моделей самое глубокое: связность выводится из координат, library-level устройства нет — библиотека **собирается** из фактического употребления | ✅ |
| [Из/в Altium](appendix/conversion-altium.md) | Модель местами богаче; компоненты разрешаются по IntLib и только по имени. Текущий проход импорта плоский; `REPEAT(…)` отвергается насовсем | ✅ |

Три страницы инструментов написаны **по одному скелету**, чтобы их можно было
сравнивать между собой: модель инструмента глазами IR → как ложатся библиотеки и
почему → что теряется → что отвергается и как это исправить в источнике → на что
обратить внимание после конвертации.

Источник для них — не память, а код: ~140 записей `import_log`, явные отказы
конвертеров и сырые заготовки в `Babel/DOC/mapping_notes.md`.
